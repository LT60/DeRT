# DeRT 结论与实践指南（收官总结）

> 一段话结论：**调度器不是万金油，它只在一段狭窄但真实存在的窗口里有价值。**
> 这个项目的全部工作，就是把这段窗口的位置、形状、漂移规律和工程化兜底测清楚：
> 位置由强模型的延迟分布决定（交叉点 ≈ 强档中位延迟 6.4s），
> 形状由任务难度分布决定（约 27% 的任务强档不可替代），
> 漂移规律决定了任何固定阈值都不稳健（必须自适应），
> 而自适应门本身的方差在预算贴着门时又会成为新的误差源（门要"慢"，数据可以抖、门不能抖）。
> 全部结论基于 **6100+ 次受控运行**（budget_main100 500 对 + sweep2 6000 条），配对设计 + McNemar 检验 + 事故隔离。

## 一、理论结论（六条可引用命题）

### P1 调度价值区间：收益集中在「预算 ≈ 强档耗时」的中段

- 预算 << 强档延迟：强档塞进预算 = 定时截断，正确率崩塌（A@3s=0，A@4s=3%）；
- 预算 >> 强档延迟：强档从容跑完，调度无增益（B≡A @30/60s，sweep2 与 main100 两轮复现）；
- 中段（预算跨着强档延迟分布）：调度把"按时且答对"的联合指标显著抬升（12s 档 87 vs 74，60s 档 90 vs 74）。
- **表述**：调度收益是「预算 / 强档耗时分布」的非线性函数，不是常数。紧预算下"快挡换强档"的收益（早期 +14pp）不可迁移——换一个任务耗时分布就消失。

### P2 交叉点定理：难度路由的价值兑现点 ≈ 强档中位延迟

- 纯难度路由（v3b）相对快档基线（C）：≤3s 显著更差（2s 档 9/60，p=2e-10），4–5s 打平，≥6s 单调更好，≥30s 突破 C 的 74% 天花板到 90%（16/0，p=3e-5）；
- 交叉点 6.4s 恰为强档中位延迟（deepseek-v4.1-flash 实测）。
- **表述**：**强模型的价值只在预算 ≥ 其延迟时兑现。** 这是本项目最硬的一条边界证据，直接回答"什么时候该用调度器"。

### P3 难度可分性：约 1/4 的任务强档不可替代，且难度可廉价预测

- 快档 correct 天花板 73–74% ⇒ 仅 ~27% 任务真需要强档；
- 难度信号（本项目中为任务语义特征）预测命中 88.9%，easy 任务 0% 误路由（690 run），hard 任务 100% 走强档（310 run），hard 任务在宽预算下 correct 96.8%。
- **表述**：难度路由的成本（误路由风险）远小于收益（天花板突破），前提是难度信号与任务域匹配。

### P4 边界漂移不变性：固定阈值对强档延迟漂移不稳健 → 自适应是必要组件

- 两轮独立证据：① sweep2 中按旧强档标定的固定时间阈值（STRONG_REMAINING_MIN=3.5s）在强档变慢后形成**路由死区**——4s 档 B 0/56 惨败 C（p<0.001）；② 同日早晚两次标定，推荐门从 7.15s 漂到 8.5s（差 1.35s）——同公式、同任务族、同一天。
- **表述**：**边界不是常数，是强档延迟分布的泛函。** 云端模型每次发布、负载波动、甚至一天内的时段变化都会移动它。因此自适应门（在线分位数 + 防漂移机制）不是可选优化，而是方案完备的必要条件。

### P5 门控方差代价：预算 ≈ 门时，门的估计方差本身是主要误差源

- v3c（在线 P60+0.5 门）实测：8s 档门短暂下探放进 14 次强档（5 次迟到）→ 66 vs v3 的 78（p=0.023）；10s 档门短暂上跳挡住 8 个难任务 → 70 vs 84（p=0.0043）。门无偏，但方差伤人。
- v3d 的四件套修正：**截尾**（剔除 wrap-up 截断样本，截断 P50=13.1s vs 自然 7.2s）、**离群修剪**（>3×窗口中位）、**限速**（门每任务最多动 ±0.3s）、**先验下限 + 单向适应**（向上跟随变慢、向下交给标定卡）。修正后 8s 档强档 0 次，全预算配对无任何一档显著劣于 v3，均值 77.2 为全部 8 策略最高。
- **表述**：**数据可以抖，门不能抖。** 在线估计器的输出要经过限速与先验约束才能用于决策——这是在线统计 → 控制信号的一般性教训。

### P6 测量纪律：悬崖区单点估计 ±15pp 不可复现

- 2–6s 悬崖预算区，行为完全相同的两个策略独立复测差异达 8–16pp（4s 档 3/18，p=0.0015）；v3@4s=82% 是幸运高值（同格独立样本 C=60 / v3b=57 / v3c=67）。
- **表述**：在悬崖区，**单格单样本的点估计不构成结论**；配对设计 + 交替轮转 + McNemar + 事故隔离（invalid/ 目录与判据）是这类评测的最低纪律。本项目三次测量事故（本机冷加载、云侧慢窗口、游戏污染）全部靠这套纪律发现并隔离。

## 二、实践指南（给工程师的 if-then）

### 决策树：你需不需要 DeRT 这套东西？

```
你的 agent 有时间约束吗（deadline / 用户等待 / 按量计费）？
├─ 没有 ──────────────────► 别做调度，直接上最强模型（P1 两端无收益）
└─ 有 ──► 预算普遍 >> 强档延迟？
          ├─ 是 ────────────► 全用强档（B≡A），调度不带来增益
          ├─ 预算普遍 << 强档延迟
          │                  ► 全用快档 + wrap-up 兜底，别硬塞强档（A@3s=0）
          └─ 预算横跨两者 ───► 上 v3d 全套（下方五步）
```

## 三、局限与未闭合（写在明面上）

1. **任务域单一 → 已部分闭合（2026-10-25 外部验证）**：主线结论来自 CMP 工具调用任务族；已接入 BFCL v4 多轮基准做第二证据源（见「三¾」），方向性结论跨域成立，但难度信号（语义词表）换域必须重标定——这条已从"猜测"升级为实证。
2. **悬崖区欠定**：4–6s 段受噪声标尺限制，只敢下"无显著差异"的结论，不敢下排序结论。
3. ~~**双档假设**~~ → 已闭合：v3e 三档在线 1000 格零回退（见三½）。
4. **漂移跟随未闭环**：用标定卡和时段差异**实证了**漂移存在（P4），但"在线分位数门能跟住多快的漂移"尚未用慢工具旋钮做系统实验。
5. **预算粒度**：未测 16–24s 段；悬崖区加密采样性价比低（噪声主导）。

## 四、token 成本视角（2026-10-24 补，现有数据可直接计算）

raw.jsonl 已记录每 run 的 `tokens_in/tokens_out/models`，无需重新采集。口径：快档（本地 Ollama）免费，成本 ≈ 强档（百炼 deepseek）调用；**每答对一题的强档成本 = 强档调用率 ÷ success%**。

| 预算档 | A 全强档 | v3b 纯难度 | v3d 时间门+难度 |
|---|---|---|---|
| 10s | 1/84 = 0.0119 | 0.31/82 = 0.0038 | 0.24/81 = 0.0030（**-75%**） |
| 12s | 1/91 = 0.0110 | 0.31/85 = 0.0036 | 0.31/88 = 0.0035（-68%） |
| 30s | 1/100 = 0.0100 | 0.31/90 = 0.0034 | 0.31/90 = 0.0034（-66%） |
| 60s | 1/100 = 0.0100 | 0.31/90 = 0.0034 | 0.31/93 = 0.0033（-67%） |

两个结论：
- **难度路由+时间门本身就是 token 成本优化**：v3d 用 ~1/3 的强档花费保住 ≥97% 的 success；
- **反例（v3b@2s）**：纯难度路由不看时间，2s 档强档率仍 31% 而 success 仅 20%，单位成本 0.0155 比 A 全强档还贵 30%——时间门避免"花强档的钱还答不对"。

### 后续优化方向（按性价比排序）

1. **三档路由（快/中/强）**：把 31% 强档里"中档就能做对"的部分降档。实验 = hard 任务族在百炼跑一个 mid 档（如 qwen-plus）@120s 宽预算看 correct 率；若 mid 接住 hard 的 30–50%，强档率 31%→15–20%，成本再近半。机制零改动：每档一张标定卡 + 一个 v3d 门。
2. **级联复核（fast-first，强档只做验证）**：快档先答，答案可疑才升级强档——把贵的"生成 token"换成便宜的"验证 token"。前置条件是需要廉价置信信号；可先用现有 raw.jsonl 的 answer/check_why 离线验证特征。**→ 服务演示层已实现第一步（2026-10-25，`service/app.py` `_run_with_rescue`）**：公共基准任务快档失败且剩余预算 ≥3s 时自动升级强档直连重跑（trigger=结构化判分失败，零成本可检测）。实测 HB/Based_0 @30s：快档 7.2s 失败 → 剩余 22.8s 升级强档 → 3 轮全过，总耗时 13.8s。正式评估口径不变（官方成绩取首次）。
3. **in-token 瘦身**：每任务 tokens_in ≈ 1.7k，其中系统提示+工具 schema 是固定开销，对强档按倍率计费时压缩提示=直接省钱。
4. **前缀缓存**：百炼 context cache 对固定前缀打折，零改动收益。
5. **记账基建（一次性小改动）**：budget_eval 目前 tokens_in/out 是全 run 聚合，只靠 models 序列推断强档占比；改为 per-call usage 按模型分记，成本口径才严格。

### 中档选型实测（probe_mid，2026-10-24 晚，n=20 hard 任务）

选「中」档是个真难题，根源是**价格与延迟正相关**：便宜的更慢，同价的没意义。解法是双门槛判定：
**① hard correct ≥ 0.8×强档；② 自身门（P60+0.8）< 强档门**——中档必须同时「接得住」且「跑得进强档进不去的预算窗口」。

| 候选 | hard correct（20 题） | P50 | 自身门 | 价格 ¥/百万（in/out） | 判定 |
|---|---|---|---|---|---|
| **deepseek-v4-flash-0731** | **100%（与强档逐题一致）** | **5.8s** | **6.6s** | 1.5/4.5（强档的 75%/56%） | ✅ **中档** |
| qwen3.8-flash | 100% | 8.9s | 10.3s | 0.8/2.7（40%） | ❌ 比强档慢——只能当「便宜强档」宽预算用 |
| qwen3.7-plus | 100% | 8.7s | 9.7s | 2/8（=强档） | ❌ 同价+更慢 |
| qwen3.5-plus | 90%（丢 2 道 T3） | 7.2s | 8.1s | — | ❌ 能力价格都不占优 |
| glm-5.3-flash | 工具调用全失败 | — | — | — | ❌ |
| 强档基线 deepseek-v4.1-flash | 100% | 6.15s | 8.5s | 2/8 | — |

结论三条：
1. **三档可行，中档 = deepseek-v4-flash-0731（同家族上代 flash）**：hard 族 20/20 全对、比强档还快 0.35s、单价约六折。强档花费（输出主导）可再降 ~40%；
2. **服务窗口扩展**：中档自身门 6.6s < 强档门 8.5s——6.6–8.5s 预算段从此能完成 hard 任务（此前该段强档塞不进、快档答不对）。三档边界：快档天花板 74%（免费）→ 中档门 6.6s → 强档门 8.5s；
3. **警示（P4 的推论）**：中档也有自己的延迟分布与漂移——三档部署 = 每档一张标定卡 + 每档一个 v3d 门，机制零改动。

工具：`eval/probe_mid.py`（两阶段冒烟/全量探针）；数据 `eval/results/mid_probe_*.json`。
局限：n=20 单样本（T3 仅 3 题）、仅 hard 族、价格为公开渠道口径（企业端点实际计费以控制台为准）。

### 三档在线对照（v3e，2026-10-24 深夜，1000 格，数据集总量 7000）

`DeadlineSchedulerV3E` = v3d 稳态门 + 中档阶梯：hard 任务按剩余预算 ≥8.5s→强档 / ≥6.6s→中档 / 否则快档。100 任务 × 10 预算档在线对照（`--with-v3e`，与 v3d/v3 同任务配对）：

| success% | 2s | 3s | 4s | 5s | 6s | 8s | 10s | 12s | 30s | 60s |
|---|---|---|---|---|---|---|---|---|---|---|
| v3e 三档阶梯 | 33 | 53 | 84 | 73 | 76 | 84 | 85 | 84 | 90 | 91 |
| v3d 双档（对照） | 32 | 60 | 82 | 79 | 84 | 83 | 81 | 88 | 90 | 93 |

- **机制完备性达成**：阶梯分派精确工作（8s 档 31% hard 走中档、10s 边界 1 个、12s+ 与 v3d 完全一致），逐档配对 McNemar 对 v3d/v3 **全部不显著——零回退**；
- **中档能力在线复现**：8s 档 31 个中档调用 correct **100%**（快档同批 ~74–80%），救回 9 个快档做不成的任务；但中档尾部延迟（P80 6.7s、max 11.1s vs 预算余量 ~7.9s）迟到 6 个、丢掉快档本可按时交付的 6 个——**9 救 6 丢，净 +1pp（n.s.）**；
- **新教训（P5 的推论）**：P60+0.8 标定卡是「能力门」不是「deadline 安全门」——P60 意味着 40% 尾部风险，直接当"塞得进剩余预算"的判据时尾部反噬。中档门需要预算感知分位数（尾部 ≤ 剩余预算）或 mid 调用级 wrap-up（v3f 方向）；
- 成本口径：12–60s 强档用量与 v3d 相同（31%），中档仅在 8–10s 介入——v3e 的价值是**打通 6.6–8.5s 服务窗口 + 三档机制完备**；直接省钱（宽预算中档降档/级联复核）= v3f。

### 三¾、外部验证：BFCL v4 多轮（2026-10-25，24 题 × 11 策略格 = 264 run）

此前 7264 次运行全部来自自建 CV 运维集——"任务覆盖面窄"是最大质疑。本轮接入 **Berkeley Function-Calling Leaderboard v4 多轮套件**（官方数据/工具类/逐轮状态判分，确定性无 LLM judge；钉 commit 见 `eval/bfcl/SOURCES.md`）。对照策略与主线同构（A 全强档 / C 全快档 / v1 时间路由 / v3d 难度+时间门，预算 {10,30,60}s）：

| 策略 | success% | 按时% | 耗时中位 | tok_in |
|---|---|---|---|---|
| A 全强档 | 37.5 | – | 23.8s | 314k |
| C 全快档 | 29.2 | – | 4.5s | 152k |
| v1@10 | **12.5**（劣于 A，p=0.03） | 8.3 | 14.5s | 129k |
| v1@30 | 33.3 | 58.3 | 26.4s | 263k |
| v1@60 | **37.5** ≡ A（+2/−0 n.s.） | 95.8 | 25.2s | 310k |

| v3d_en 英文重标定 @30/60 | 29.2 | 95.8–**100** | 4.8s | 165–179k |

四条外部结论：

1. **宽预算 B≈A 跨域复现**：v1@60 与 A 逐题仅 2 个不一致（n.s.）——P1 的「调度不劣于全强档」在第二任务域成立；
2. **紧预算悬崖跨域复现**：v1@10 = 12.5%（粘性强档撞上小预算，与主线 2–3s 档病理同源）；
3. **v3 的结构性修复外部有效**：v3d/v3d_en 在 10s 档仍 29.2%（=C，无悬崖）且按时率 87.5–100%——「难度路由+快档优先+时间门」结构在紧预算下不坠落，v1 结构做不到；
4. **两条新边界（升级为实证）**：①难度信号不可跨域直接迁移——中文词表在英文基准恒不触发（≡C），重标定是部署必做项；②**强模型价值是域依赖的**——BFCL 上 A−C 仅 +8.3pp（自建集 +27pp），难度路由的收益天花板由 A−C 差决定，域内标定（P3 的 88.9% 命中）不能外推天花板。

工具链：`eval/bfcl_adapter.py` / `eval/bfcl_run.py` / `eval/analyze_bfcl.py`；数据 `eval/results/bfcl_bfcl_ext1/`；图 `docs/figures/bfcl_ext_curves.png`。
局限：24 题样本小（除 v1@10 vs A 外全部 n.s.）；判分语义与自建集不同（逐轮状态比对 vs 数值规则），跨域比的是**方向**不是点值。

### 三¾½、难度评分通用化（2026-10-25 晚，用户指令：难度评分应使用公用通用方案）

## 五、两个绕不过去的质疑

### 防御性问答：如果只看「最终做对与否」，DeRT 有什么优势？

答：**在无时间约束、不算钱的世界里，确实没有**——全强档就是 success 上限，DeRT 从不声称比强模型更准。调度问题的定义前提就是资源约束，优势函数在三种真实约束下分别非零：

1. **时间是硬约束（紧预算）**：全强档不是「success 低」而是「不存在」——强档中位延迟 6.4s，2–4s 预算下每次都超时（按时 success = 0）。实测：2s 档 A=0% vs v3emp=31%，8s 档 71% vs 81%，10s 档 v3emp 94% **显著反超** A 84%（p=0.03，A 有任务迟到）。约束越紧，调度优势越大——与操作系统 CPU 调度、网络 QoS 同构。
2. **钱是约束（宽预算）**：success 持平（v3emp 96–97% ≈ A 100%，n.s.）但强档用量 27% vs 100%——同等正确率下 3–4 倍成本差。这个优势的量纲是钱，看 success 指标看不见它。
3. **评分函数本身**：主线 success 从来是「deadline 内做对」而非「最终做对」——真实系统里超时即失败（用户流失、SLO 违约、下游阻塞）。

诚实边界：若场景是离线批处理、时间无限、只求最准，全强档就是最优解，DeRT 无存在价值。DeRT 的定位是 **deadline-aware runtime**——目标场景是用户在等的交互式 agent。一句话总结：**没有资源约束，就没有调度问题；约束越紧，调度越值钱。**

### 防御性问答 2：方案本质是「限定时间」，但优势只在特定预算区域，且边界位置无法先验知道——这方案真的有实际意义吗？泛用性怎么提升？

答：质疑成立的部分先承认，不成立的部分正面反驳。

**①「边界位置无法先验知道」不是方案的缺陷，恰恰是方案存在的理由。** 如果边界位置已知且固定，一条 if 语句就够（"预算>8.5s 用强档"）——不需要调度器。但 sweep2 实证了边界会漂移（强档后端一换，8s→10s）且固定阈值会出死区（4s 档 B 0/56 惨败 C）。整个项目的机制演化（v1 纯时间 → v2 滑窗 → v3d 稳态门 → v3emp 影子难度）就是在解「无法先验」这一个问题。把「位置未知」当无效证据，等于说「因为不知道边界在哪，所以不该有找边界的机制」——逻辑反了。价值区间窄也是一切调度器的常态：TCP 拥塞控制、OS CPU 调度都只在资源紧张时有意义，没人因此说它们没用。

**②「显式 deadline 不真实」是真正的软肋，承认。** 真实用户很少输入"30s 预算"。泛用性提升四条路线（按成本排序）：

1. **显式→隐式预算（零成本，机制已备）**：按交互类型给默认预算先验——聊天补全 15s（用户等待流失阈值）、后台批处理 600s、CI 检查 300s、API SLO 由调用方传。用户无感，deadline 依旧存在，只是由系统代设。服务已支持 deadline 参数，补一张预设表即可。
2. **先验路由→后验升级（低成本，已有雏形）**：不预测难度，fast-first 级联——快档先试 + 廉价失败检测 + 剩余预算升级强档（服务化⑧救援已实现）。泛化关键在把失败检测从「结构化判分」扩到自由任务（自洽性/轻量验证器，有成本）。这条路完全绕开「边界在哪」的问题：错了有保险，边界就不必先验。
3. **量纲泛化（中成本，机制同构）**：把「剩余秒数」抽象成任意资源量纲——token 成本、能耗、并发槽位。调度三元组不变：估计每个选项的消耗分布 + 剩余预算 + 难度。故事从「快」升级为「约束感知运行时」，代码改动集中在预算扣减一处。
4. **难度史跨任务泛化（高成本，真泛化）**：目前影子难度按 task_id 隔离，同任务重复才受益。两条子路：a) 任务嵌入近邻继承难度先验（预注册分层已证手写类别太粗 F1 0.37，须在 embedding 粒度做）；b) 快档过程自评信号（首 token 犹豫度/工具调用缺失），零历史依赖但属新增信号源。

**③「只在重复任务上有优势」值得正面定价而非辩护**：生产级 agent 任务流重复率天然高（客服、运维、RAG QA 同模板问法），影子流量在那类场景是常态而非特例——HB 回放显示第 2 轮就收敛到 A 级。真·一次性任务的世界里，任何学习方法（包括词表）都同样失效，这不是本方案特有的边界。

一句话：**DeRT 不预测边界在哪，它假设边界会漂移并为此造了跟随机制；泛用性的正确方向不是「让一个 deadline 方案适配所有场景」，而是「预算的来源泛化（隐式）+ 量纲泛化（成本/能耗）+ 难度信号泛化（跨任务）」三条线，各按需取用。**

> 2026-10-26 更新：路线 1 之外的 2（级联）与量纲泛化（成本）已被离线实验验证可行——见「三⅘」节与 `docs/figures/generalization.png`。

### 三⅘、泛用性验证：验证层（级联）+ 成本量纲（2026-10-26，全部离线零 API 成本）

承接防御性问答 2 的四条泛化路线，本轮用离线实验验证了前两条。**五层视角**：执行（快档先试+收尾）/验证/升级/记忆（影子史）/路由——已有四层，唯一缺口是验证层（发现「这次猜错了」），它是新任务冷启动唯一的事后补救机会。

**实验 A：judge 体检（`eval/judge_audit.py`，120 样本 = CV 100 + HB 20）**：快档 qwen2.5:7b 当判卷老师（只看问题+回答，temp=0，延迟 P50 0.44s），对照规则判分真值。预注册通过线：召回≥0.60 且误报≤0.25。

| 提示词 | 召回(抓错) | 误报率(错杀) | 判定 |
|---|---|---|---|
| v1 严格版（"宁可存疑"） | 96.3% | 64.4% | FAIL——错杀太多，级联成本爆炸 |
| v2 中性版 | **96.3%** | **13.7%** | **PASS** |

HB 域 v2 召回 94.7%（18/19）。**教训：judge 先验由提示词决定，一句话就把误报从 64% 压到 14%——judge 校准是验证层的必要工序；且召回/误报是可调旋钮，按「漏检代价 vs 升级代价」之比选工作点。**

**实验 B：级联端到端离线模拟（`eval/replay_cascade.py`）**：快档先试（C 实测）→ judge v2 → 带门升级（剩余预算 ≥ 强档 P50 3.03s 才升级，否则原样交付；预算连判卷都装不下则跳过判卷直接交付）：

| 预算 | 带门级联 | 升级率 | A | C | B | 强档成本/对题（级联 vs A） |
|---|---|---|---|---|---|---|
| 3s | 37 | 0% | 48 | 37 | 43 | 0 vs 0.0119¥ |
| 8s | 71 | 10% | 98 | 72 | 95 | 0.0007 vs 0.0058¥ |
| 30s | **98** | 35% | 100 | 73 | 100 | **0.0019 vs 0.0057¥** |
| 60s | **99** | 36% | 100 | 73 | 100 | 0.0019 vs 0.0057¥ |

宽预算域 98–99 ≈ A−2（达预注册线）且强档成本/对题是 A 的 **1/3**；紧预算优雅退化到 C（3s 档零升级）。judge 失误拆解：漏检 1（T2-21 错答案被放行）、错杀 10（对的被升级——浪费钱但不致错，印证代价不对称设计）。

**实验 C：成本量纲回放（`eval/replay_cost.py`）**：tokens×公开价（¥2/M in ¥8/M out），预算横轴从秒换成元：**v3emp′ 全程 ≥ A′**——0.010¥ 即 100/100 封顶（A′ 需 0.020¥），强档率恒 27%。机制红利：价格精确已知不漂移 → **成本量纲不需要 v3d 的自适应门**（时间会漂移，价格不会）。

**综合结论：两个「赌博」的解法都被数据支撑**——赌博二（新任务猜错）在宽预算由级联兜底（A 级正确率、1/3 强档成本），升级事件自动记入影子史（第二次起路由直上强档）；赌博一（预算任意）在成本量纲下由 v3emp′ 直接消解。图 `docs/figures/generalization.png`。

边界如实交底：①级联只作用于宽预算，8s 以下升级窗口不足（快档试错烧时间——mid-run 中止升级是后续工作）；②judge 错误类型偏「未完成/跑题」类，幻觉数值类「自信地错」未单独测；③模拟的升级路径用 A 历史结果近似真实重跑（同任务从零跑强档，语义一致但偏乐观）；④价格用百炼公开价，实际账单或有出入。

### 三⅘½、v4 自动档上线（2026-10-26 下午）：deadline 从「输入」降级为「高级覆盖」

用户三轮质疑（「输入限定时间不智能」→「场景耐心不可行」→「负载不归 agent 管」）收敛出的定案：**永不问时间，交付条件=判卷通过**。已实现为服务默认交互：`deadline` 不填即自动档——影子史命中 hard 直接强档直上（熟客效应）；否则快档先试 → 本地判卷（v2 校准提示词，P50 0.44s；Ollama 不可用降级原样交付）→ fail 升级强档重答 → 记账复用 record_shadow。真实冒烟闭环：剧本任务首跑 22.9s（判卷真抓出「回答中没有提供实际的查询结果」→升级强档）→ **同任务再跑 0.16s 强档直上**（熟客效应端到端生效）。时间智能从接口层退到模型层：各档延迟、任务难度、升级收益全是系统自知的内部量，交付时以解释呈现（「快档一次通过 4.2s」/「升级强档 13.8s」），不以表单形式索取。**叙事一句话：deadline 不是输入，是交付条件的影子。**

## 六、数字速查（写作引用时防止口径漂移）

- 主结果 A/B/C @3/8/30/60s（main100，N=100 配对）：A 48/98/100/100；B 43/95/100/100；C 37/72/73/73
- sweep2 全量：6000 run，八策略；v3b vs C @30s 16/0 p=3e-5；v3b vs C @2s 9/60 p=2e-10
