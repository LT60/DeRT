# DeRT 基准任务集设计

## 设计原则

- 任务全部基于模拟实时检测系统（延迟测量、检测质量），合成数据 + 可控工具延迟——零外部依赖、完全可复现，且延迟分布可按实验需要构造
- 每个任务有唯一可判定的成功标准（客观答案或可校验的产物）
- 时间预算是任务的输入参数，不是环境常量

## 任务分层（共 60 个，2026-09-28 由 50 扩到 60）

| 层 | 数量 | 定义 | 示例 |
|---|---|---|---|
| T1 简单查询 | 20 | 单工具、单轮问答 | "【配置核对】当前检测服务的输出分辨率与帧率分别是多少？" |
| T2 单步诊断 | 20 | 需调用 1–2 个工具并推理 | "【告警·延迟】最近 200 帧（约 3.3 秒）的 P95 延迟是多少毫秒？是否超过 15ms 的 SLO 红线？" |
| T3 复杂诊断 | 20 | 多工具依赖链（≥2 个工具），需规划调用顺序 | "【录像排查·依赖链】先列出所有已录制片段，再查询其中第一个片段的延迟 P95——片段 id 只能从目录里取" |

### 措辞口径（2026-09-28 定，此前措辞被评价为"不通俗也不专业"）

三条纪律，改任务时必须遵守：

1. **场景前缀**：每条任务带 `【配置核对】/【巡检采样】/【告警·延迟】/【值班工单】/【关联诊断】` 等前缀，交代"为什么要问"，而不是凭空提问。
2. **双单位**：帧数必须换算成时间——写成"最近 200 帧（约 3.3 秒）"。只给帧数外行读不懂，只给秒数又与工具参数对不上。
3. **阈值类任务不得更换判断触发词**：判分器的 `above_verdict` 靠答案里的方向词判对错，只认"超过/未超过/低于/达标/突破"这一族。问句写成"是否突破 15ms 红线"，模型就会答"未突破"——**内容全对也会被判错**。SLO、告警、值班这些包装词可以随便加，"是否超过/是否低于"不能换。
4. **阈值类用标准语序「是否超过 X」，不要用「对照 X 是否超过」**：后者是 2026-09-28 改写时留下的歧义语序（"对照 25ms 健康线是否超过"），读起来像是让模型判断别的命题。已全部统一为"是否超过 25ms 健康线？"——触发词不变，判分逻辑不受影响。
5. **措辞效果禁止用单次 A/B 定案**：本地 7b 采样波动极大，同一条 prompt 两次跑可以是 1.16s 判对、10.67s 判错，看起来像"改措辞修好了/改坏了"，实际是噪声。2026-09-28 就据此误判过一次（以为"配置"二字能阻止 T1-1 跑题，两轮全量验证证明无关）。措辞调整一律以**全量验证 + 多重复**为准。

### 工具覆盖（8/8）

工具集 8 个工具，2026-09-28 前基准只覆盖了 4 个（`alarm_log`/`gpu_stats`/`list_segments`/`segment_latency` 从未出现在任何任务里，导致依赖图与并行执行器的成果在正式评估中等于没被验证）。新增的 T3-11…T3-20 补齐覆盖，并刻意构造两类调度场景：

- **依赖链**：`list_segments → segment_latency`（片段 id 只能来自目录，猜不出来）
- **并行批**：多个互不依赖的工具（如同时要报警日志 + GPU 状态 + 延迟指标），逼执行器同批并发

2026-09-28 全 60 条本地验证实测确认：8 个工具全部被真实调用，其中 `list_segments` 由 **T3-11 与 T3-19** 触发（这两条的问句不点名片段 id，模型必须先查目录）。T3-12 / T3-18 的问句直接写了 `seg-001`/`seg-002`，模型不必查目录也能作答，故其 `expect_tools` 不列 `list_segments`——这两条的价值是"两次 `segment_latency` 并行批"与"`segment_latency → render_report` 串联"，不是依赖链。

### 判分器自测

`python -m eval.tasks` 跑三层自测，任何一层不过即 FAIL。判分器是整个评估的地基，三类静默故障必须靠自测拦住：

1. **可达 + 非空判**：按问句里的参数真实调用 `expect_tools` 拼出"该拿到的答案"，验证每个判分器既**可达**（金答案判得过）又**非空判**（无关文本判不过）。新增判分器必须先过这一关——静默的空判会把成功率系统性抬高。
2. **复述变体（防假阴性）**：金答案是"工具原始输出拼接"，措辞跟模型自然回答差别很大。2026-09-28 实测抓到 T1-5：模型答「当前服务配置的运行模式是实时流模式」内容完全正确，判分器却死等英文原词 `realtime-stream`，把正确答案判成错。故对"照抄固定字符串"类的判分额外喂人类口吻的答案变体（"RT-Detect V2"、"推理超时报警"等），确保**判的是内容而不是表述**。
3. **压缩白名单覆盖**：金答案过一遍 `select` 压缩器后仍必须判得过。若 `src/context.py` 的字段白名单漏了某个判分字段，`dert_full` 策略下该任务就是必挂——测到的是白名单 bug，不是压缩策略效果。2026-09-28 靠这层抓出 `detection_stats` 漏 `mean_targets_per_frame`（影响 5 条任务）、`alarm_log` 丢 `msg`（影响 T3-14）。

### 难度校准（2026-09-28 实测）与"故意不修"的三件事

两轮全 60 条本地验证（qwen2.5:7b，deadline=60s 近乎无限预算）：

| | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 判分通过 | 46/60（77%） | 45/60（75%） |
| 被标记条数 | 16 | 15 |

总量稳定在 ~75%，但**单条任务在两轮之间来回翻转**（T1-12/13/15 第 2 轮新败，T1-14/T2-11/15/20 转胜）。故正式网格必须多重复取均值——单轮数字不可信。

强档对照（deepseek-chat，deadline=30s，只跑 7b 判错的 14 条）：**14/14 全过，全部 2 步、1.3–3.1s**。这证明失败是 7b 的能力上限，不是任务集或判分器的问题。

失败构成里占大头的是**跑题**：模型先调对了工具、拿到正确数据，却不收尾，继续调无关工具，最后把最后一个工具的输出当答案（如 T1-14 问"每张图检出几个目标"，答的是 GPU 状态）。据此有三件事**故意不修**：

1. **不给 T1/T2 加"只准调用 X 工具"的约束**。加了等于替模型做工具路由，基准就测不出"选工具要花多少时间"；更关键的是它会抹平 qwen 与 deepseek 的差距（deepseek 从不跑题，qwen 才跑题），而那个差距正是 DeRT 路由要吃的空间。
   - 例外：T3-13/14/15 加了收窄，理由是那三条曾跑出 **395s 不收敛**，属于测量灾害（单次运行足以污染整档统计），不是难度梯度。二者性质不同。
2. **不修 7b 的数值比较错误**。T2-3/7/8 问"P99 是否超过 25ms"，7b 把 22.26 / 16.81 / 17.67 都答成"超过"。deepseek 同题全对，属模型能力差异，是基准该测的东西。
3. **不为提高成功率而放宽判分器**。判分器只能往"更不容易误杀正确答案"的方向改（如 T1-5 收中文写法），不能往"更容易判过"的方向改。

## 指标定义（每次运行记录）

| 指标 | 定义 |
|---|---|
| 任务成功率 | 60 任务中达成成功标准的比例 |
| E2E 延迟 P50 / P95 | 从任务下发到最终回答的端到端延迟 |
| TTFT | 首个 token 返回时间 |
| 单工具耗时 | 每次工具调用的墙钟时间（含排队） |
| Token 成本 | 输入 + 输出 token 总量（按模型分档计） |
| 降级触发率 | 强模型→快模型路由的触发比例 |
| 预算超支率 | 实际耗时超出预算的任务比例 |

延迟测量方法论：所有延迟统计排除"任务下发到下一次处理开始"的等待时间，只计有效处理段。

## 运行矩阵

2026-09-28 正式网格（60 任务版）：

| 策略 | 运行次数 | 说明 |
|---|---|---|
| `fixed_fast`（qwen2.5:7b） | 60 × 3 = 180 | 行为与预算无关，跑 1 次后对 4 档分别判按时 |
| `fixed_strong`（deepseek-chat） | 60 × 3 = 180 | 同上 |
| `dert`（v0：快档 + wrap_up） | 60 × 4 × 3 = 720 | 每预算每重复各 1 次 |
| `dert_v1`（v1.1 双档路由） | 60 × 4 × 3 = 720 | 当前最优配置 |
| `dert_full`（v1.1 + select 压缩） | 60 × 4 × 3 = 720 | 架构第四模块的正式数据 |
| **合计** | **2520** | 全实时、禁用缓存 |

每配置重复 3 次取均值——本地 7b 逐次波动能把同一任务从判对翻成判错（见「难度校准」），单轮数字不可信。快档本地运行零成本；强档调用约 1260 次（180 基线 + v1/full 在 4s 以上档位各约 540），成本上限约 ¥15。

`dert_v2` 不在本网格内：它是 2026-08-25 在 **50 任务集**上测出的负结果（-5pp），已如实记录在 README；重测要多花约 30% 成本且不产生新结论，故保留代码供复现、不重复测量。跨数据集数字不可混用，README 中已分别标注。

## 评估成本控制：transcript 缓存复用（借鉴 Reasonix replay）

Reasonix 的 `replay` 命令可在零 API 费用下复现基准 transcript。DeRT 评估采用同思路压缩强档模型的调用成本：

- **响应缓存**：LLM 调用按 (模型, 输入消息哈希) 缓存。600+ 次运行中，不同策略的配置仍会产生大量相同前缀调用（T1/T2 任务的固定输入、同温度下的确定性输出）
- **延迟口径一致性**：缓存命中时，墙钟耗时按该调用历史 P50 回放并标记 `cache_hit=true`，保证统计口径统一，不把缓存读取速度（毫秒级）混入延迟分布
- **两轮制**：开发迭代期全部走缓存（快、免费）；**最终 Pareto 曲线必须包含至少一轮全实时运行**，避免缓存回放的估算值系统性偏乐观
- 成本上界控制：先以 10 任务 × 1 预算档实时试跑测出单次成本，再定重复次数（3 次为上限，超出即砍）
